# BLE Protocol Notes

This document summarizes the protocol knowledge that the app relies on. It is an interoperability document, not a claim that every compatible-looking scooter implements every command.

The current per-family reference is [Vicont communications](ble/VICONT.md); the [BLE index](ble/README.md) records actual implementation/support scope. This page records the original-client evidence behind the Flutter integration.

## Evidence labels

- **Confirmed from source**: behavior was traced to the original companion application's client logic.
- **Confirmed by capture/device**: behavior was observed in BLE traffic or device responses.
- **Inferred**: the interpretation fits the available evidence but still needs a live capture or broader hardware testing.

## Transport

The original-client findings identify two candidate GATT layouts: `FEE0/FEE2` and `FFF0/FFF1`. The transport prefers `FFF0/FFF1` when both are available, requests MTU 255 on Android, and subscribes before handshaking. iOS writes prefer an ATT response; Android prefers no response. See the [connection audit](ble/CONNECTION_AUDIT.md) for the corrected setup behavior. These candidate layouts are not evidence of a complete hardware support matrix.

## Frame shape

Normal application frames use a compact structure containing a protocol marker/state byte, command code, payload length, payload bytes, and a checksum. [The Vicont codec](../flutter_app/lib/integrations/vicont/vicont_codec.dart) is the source of truth for frames generated by this project. A small number of handshake packets are treated as literal protocol constants because the original client sent them that way and they do not all fit the normal checksum rule.

## Incoming telemetry

The decoder currently recognizes these families when a scooter reports them:

| Code | Data represented in the app |
| --- | --- |
| 16 | Live motor/battery telemetry such as speed, voltage, battery percentage, and temperature |
| 17 | Status flags, odometer-related state, lock state, gear/unit flags where present |
| 18 | Dashboard/controller hardware and software versions |
| 19 | Throttle and brake sensor values |
| 31 | Battery-management-system information |
| 60-63 | Current configuration/read-back values |
| 74 | Dashboard/work-mode response where supported |

Fields are nullable in [Telemetry](../flutter_app/lib/core/telemetry.dart). A missing field means the app has not received a trustworthy value; the UI should show an unknown state rather than a guessed default.

### Motor and dashboard readings

**Confirmed from source:** the original client's motor-frame decoder uses the following offsets into the DATA payload (all multibyte integers are big-endian):

| DATA bytes | Reading | Conversion |
| --- | --- | --- |
| 0–1 | Voltage | raw × 0.01 V |
| 2–3 | Current | raw integer; units unconfirmed |
| 4–5 | Speed | raw × 0.1 km/h |
| 6 | Battery percentage | integer |
| 7 | Controller temperature | integer °C |
| 8 | Motor temperature | integer °C |
| 9 | Battery temperature | integer °C |
| 10–11 | Motor speed | raw integer; units unconfirmed |

The dashboard receives these code-16 readings along with the trip/odometer fields from code 17. A valid zero is displayed as zero. When a short frame omits a field, the decoder keeps its last observed value; fields never received remain unknown. These are last-reported readings, not a claim that every model has every sensor. Code 31 BMS temperature has unconfirmed units and is not substituted for the motor frame's battery temperature.

## Toggle polarity

Several controls in the original client send a value derived from the **current** state, not the desired state. This distinction matters because reversing it can produce an acknowledgement/beep without changing the scooter. [VicontCommands](../flutter_app/lib/integrations/vicont/vicont_commands.dart) maps semantic desired states to the equivalent wire values; the controller waits for status before allowing state-dependent toggles.

**Confirmed from source:** the original companion application's bundled JavaScript (`app-service.js`) was inspected for the home-screen sender and status decoder. Extracted application files are not part of this repository. The home screen calls `sendSwitch(53, bleDeviceInfo.startingModeState)`. Its switch is labelled `零启动` (zero start) in both visual states, and its checked value is `1 != bleDeviceInfo.startingModeState`. The status decoder reads `startingModeState` with `n.substr(-6,1)`, i.e. code 17, DATA byte 0 bit5. The shared sender uses `[1 == currentState ? 1 : 2]` for code 53.

Consequently bit5=1 sends `[1]` to request zero start, while bit5=0 sends `[2]` to leave zero start. Calling the complementary bit5=1 state **kick start** is an interpretation of the original zero-start switch, not an English label found in that source. This app uses the fixed button label **Kick start**, with active styling when bit5=1, as requested. It retains the reported state while waiting for a matching status frame; a code-53 acknowledgement alone does not establish that the mode changed.

**Unverified on hardware:** which models, firmware versions or regional configurations permit changing start mode. No model/country unlock command has been established. A timeout reports the lack of confirmation and leaves the reported state visible; feature visibility switches do not bypass firmware restrictions.

## Configuration read-back

Codes 60-63 can be queried so the app can display the value actually reported by the scooter after a write. Torque/brake display values are not simple raw bytes; the original client uses command-specific scaling on write and command-specific divisors on read-back. The app mirrors those confirmed conversions rather than applying one shared formula.

**Confirmed from source:** `[0]` queries these settings and `[255]` restores defaults. Zero must not be presented as a writable 0 km/h limit. Speed values are sent as whole km/h even when the scooter's display is using miles.

**App range, not hardware-confirmed support:** speed selection is 1–31 km/h. This is the app's selectable range; actual acceptance and achievable speed depend on the controller. The UI displays the reported value separately, preserves out-of-range read-backs, and reports a different returned limit or a timeout. A silent timeout resyncs sliders to the last reported settings even when a follow-up query also receives no reply.

## Feature discovery

The original application receives model-specific feature visibility from a remote service. No equivalent complete capability bitmap has been confirmed over BLE. This app records advertised names, protocol selection, discovered GATT service/layout and available firmware integers in a local model database. Matching catalogue entries can choose UI feature defaults and artwork; explicit per-device overrides take precedence. The bundled entry is an unconfirmed family fallback, not an exact-model identification or a firmware unlock. User-created model entries are labelled user-defined. See [protocol integrations](ble/ADDING_A_PROTOCOL.md) and [model records](MODELS.md).

The Flutter BLE transport is shared across registered protocol integrations. The existing Vicont-family framing, decoding, commands and binding acknowledgement now live in `flutter_app/lib/integrations/vicont/`; new integrations supply independent sessions and GATT profiles. The production registry currently includes this family only. A synthetic second protocol is tested without claiming another real scooter is supported. No new wire-level capability or model-identification claim follows from this refactor.

## Known unknowns

- The semantic purpose of every byte in the post-connect handshake is not known.
- Optional compartment controls appear model-dependent and lack a confirmed persistent state report.
- Some response layouts differ by firmware or model and need more real-device captures.
- A protocol observation on one scooter should not automatically be generalized to every scooter sharing the same BLE naming pattern.

## Contributing protocol findings

A useful protocol contribution includes the scooter/model context, firmware versions if available, the exact action performed, relevant TX/RX frames with personal device identifiers removed, and whether the conclusion came from a source trace, live capture, or inference. Avoid documenting guesses as established behavior.
